# Сжатая developer-версия ТЗ (1–2 страницы)

## Цель
Собрать Telegram-бота продаж с 4 категориями товаров (`SIM`, `GU`, `BANK`, `used_gu_auto`) и 3 ролями (`buyer`, `worker`, `admin`), где:
- есть каталог с фото и полными карточками,
- оплата проходит внутри бота,
- ручные и автоматические сценарии выдачи разделены по категориям,
- назначения заказов происходят только работникам с активной сменой,
- весь UI-текст и подписи кнопок редактируются из админки без правок кода.

## Ключевые бизнес-потоки
1. **Покупка:** каталог → товар → параметры/сумма → счет → оплата → сценарий категории.
2. **SIM:** после оплаты обязательный ICC-ID (одним сообщением, строками) → назначение активному worker → работа с дедлайном 3 часа → загрузка договоров → выдача пользователю.
3. **GU/BANK:** после оплаты назначение активному worker → диалог buyer/worker в рамках заказа (текст/фото/документы) → завершение.
4. **Использованные GU:** после оплаты авто-выдача txt из стока (по строкам), маркировка использованного.

## Роли и смены
- `worker` и `admin` — независимые роли; возможна комбинация `admin+worker`.
- Автоназначение заказов только пользователям с ролью `worker` и активной сменой.
- Если у пользователя только `admin`, автоназначений нет.
- Смены: старт/стоп через подтверждение, хранить интервалы в `work_sessions`.

## MVP-модули (обязательно)
1. Каталог, категории, карточки товара с фото.
2. CRUD категорий и товаров в админке.
3. Оплата + безопасная обработка статусов (без двойного зачисления).
4. SIM: прием ICC-ID, назначение, продление (+1/+3/+6), дедлайн, договоры.
5. GU/BANK: order-чат внутри бота.
6. Used GU: загрузка txt-стока, авто-выдача txt.
7. Роли и управление ролями через бота.
8. Смены работников и worker-статистика.
9. Разделы: все/активные/исполненные заказы.
10. Рейтинг покупателей (1..5) после завершения заказа.
11. Массовая рассылка.
12. Модуль «Тексты и кнопки» с `system_key`-логикой.

## Рекомендуемая архитектура
- **Framework:** aiogram 3.x (FSM + routers)
- **DB:** PostgreSQL + SQLAlchemy (async)
- **Cache/FSM:** Redis
- **Слои:** handlers → services → repositories → models
- **Пакеты:** `admin/`, `worker/`, `user/`, `handlers/`, `services/`, `repositories/`, `models/`, `database/`, `keyboards/`, `middlewares/`, `utils/`, `config/`

## Минимальная схема данных
- `users`, `user_roles`, `work_sessions`
- `categories`, `products`
- `orders`, `order_messages`, `order_files`
- `payments`
- `stock_used_gu`
- `rating_history`
- `replacements`
- `broadcasts`
- `ui_texts`, `ui_buttons`

## Статусы заказа (рекомендуемый набор)
`Новый`, `Ожидает оплаты`, `Оплачен`, `Ожидает ICC-ID`, `ICC-ID получены`, `Назначен исполнителю`, `В работе`, `В диалоге`, `Ожидает договоры`, `Исполнен`, `Отменен`, `Просрочен`, `Возврат средств`, `Замена запрошена`, `Замена одобрена`, `Замена отклонена`.

## Критичные требования к надежности
- идемпотентность платежей;
- логирование критичных действий (оплаты, роли, смены, рейтинги, статусы заказов);
- защита от повторной выдачи стока;
- хранение истории статусов/переписки/файлов по заказу.

## Критерии готовности
Проект принят, если:
- все 4 сценария категорий работают;
- назначение заказов учитывает смены;
- админ управляет ролями/категориями/товарами/стоком/рассылкой;
- worker работает с дедлайнами и завершением;
- покупатель видит профиль, историю, рейтинг;
- UI-тексты/кнопки редактируются без изменения кода.
